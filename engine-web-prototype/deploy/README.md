# Размещение Sacura

Стек редактора: React/Vite → Nginx → Node.js API → SQLite и приватный S3. Вход использует логин и пароль; регистрация доступна только по одноразовому приглашению. У каждого аккаунта свои проекты, история сохранений и доступ к загруженным мешам. Пароли хранятся как хеши scrypt; сессии — в SQLite и HttpOnly cookie (30 дней).

## Локальный контейнерный запуск

Понадобятся запущенный Docker и Docker Compose 2.24+ (production override использует `!reset`). Из папки `engine-web-prototype` (сначала `cd engine-web-prototype` из корня репозитория):

```sh
cp .env.example .env
openssl rand -hex 32
```

Запишите случайный секрет в `S3_SECRET_KEY`. Для новой установки укажите `APP_USER` и `APP_PASSWORD`: сервер создаст первый обычный аккаунт, который затем сможет приглашать других. После первого запуска эти значения можно очистить; существующий пароль это не меняет. При обновлении старого хранилища укажите прежние значения: общие проекты будут привязаны к этому аккаунту. Без них старые проекты сохранятся в базе без владельца и не будут видны новым аккаунтам. `.env` исключён из Git и контекста Docker. Далее:

```sh
docker compose up -d --build
docker compose ps
```

Откройте http://localhost:8080 и войдите с `APP_USER`/`APP_PASSWORD`. В главном меню выберите «Пригласить пользователя» и скопируйте созданную ссылку. Порт по умолчанию слушает только loopback. API, SQLite и MinIO не публикуют порты наружу. Модели доступны через авторизованный API; публичная политика бакета и CORS S3 не нужны. SQLite хранится в томе `sacura_projects`, MinIO — в `sacura_meshes` (при стандартном имени Compose).

Новый аккаунт начинает с пустого проекта. Для переноса старого браузерного проекта экспортируйте JSON со старого редактора и импортируйте через «Файл → Открыть проект». Модели из него будут вынесены в S3 при сохранении. Обычный `npm run dev` сохраняет прежний режим браузерного прототипа.

В контейнерной версии:

- Автосохранение в SQLite через 1,2 секунды после изменения; Ctrl+S сохраняет сразу.
- «Файл → Открыть с сервера» показывает сохранённые проекты. При перезагрузке открывается последний выбранный проект этого браузера.
- «Сохранить как» создаёт независимый проект в БД.
- GLB и OBJ до 3 МБ хранятся в S3. Одинаковые файлы используют один объект, идентификатор — SHA-256 содержимого.
- Экспорт JSON и шаблона встраивает модели обратно, чтобы файл можно было открыть без исходного сервера.
- При конфликте вкладок сохранение прекращается с сообщением. Экспортируйте свои изменения, откройте актуальную серверную версию и при необходимости импортируйте экспорт как новую копию. Закрытие вкладки до завершения автосохранения может потерять последние изменения; дождитесь «Сохранено на сервере».
- БД хранит последние 20 версий каждого проекта в `project_versions`. Шаблоны редактора и раскладка интерфейса по-прежнему локальны для браузера. Аудио и изображения остаются внутри проекта; лимит JSON-запроса — 32 МБ.

## Сервер и HTTPS

Для Ubuntu 24.04/26.04 LTS установите Docker Engine из [официального apt-репозитория](https://docs.docker.com/engine/install/ubuntu/) вместе с `docker-buildx-plugin` и `docker-compose-plugin`. Node.js на VPS не нужен: клиент и API собираются внутри контейнеров. Проверьте `sudo docker version` и `sudo docker compose version`; нужен Compose 2.24+. Сборка MinIO из исходников требует свободного места и памяти, поэтому перед установкой проверяем `df -h`, `free -h` и архитектуру `uname -m`.

Для развёртывания подготовлен скрипт (из `engine-web-prototype`):

```sh
cp .env.example .env
chmod 600 .env
# Заполнить S3_SECRET_KEY, DOMAIN и ACME_EMAIL в .env.
sudo bash deploy/production.sh check
sudo bash deploy/production.sh deploy
sudo bash deploy/production.sh status
sudo bash deploy/production.sh logs
```

Скрипт проверяет конфигурацию без вывода секретов, сначала собирает образы, при обновлении создаёт снимок существующей SQLite-БД и ждёт готовности контейнеров. Тома не удаляются. После запуска проверьте публичный `https://ваш-домен/api/health` и вход в редактор: готовность Caddy-контейнера ещё не подтверждает выдачу сертификата. Снимок SQLite остаётся в `/data/backups`; его нужно отдельно скопировать с VPS вместе с резервной копией моделей. Логи контейнеров ограничены тремя файлами по 10 МБ на сервис. Nginx обновляет DNS API, поэтому пересоздание API при обновлении не требует ручного перезапуска веб-сервера.

Для подключения позже нужны адрес VPS, SSH-порт, пользователь с `sudo`, способ SSH-аутентификации и домен. Перед переносом проверяем существующие сервисы и занятые порты; домен должен указывать на VPS. При передаче файлов включайте текущую папку `engine-web-prototype`: несохранённые в Git изменения не попадут на сервер через обычный `git clone`.

На VPS установите Docker, скопируйте репозиторий, перейдите в `engine-web-prototype` и заполните `.env`. Направьте DNS A/AAAA домена на VPS, откройте TCP 80/443 и UDP 443, заполните `DOMAIN` (например `editor.example.com`, без схемы) и `ACME_EMAIL`. Запустите:

```sh
docker compose -f compose.yaml -f compose.production.yaml up -d --build
docker compose -f compose.yaml -f compose.production.yaml ps
```

Caddy автоматически получает и обновляет TLS-сертификат. HTTP перенаправляется на HTTPS. Откройте `https://ваш-домен`. Производственная конфигурация убирает прямой порт редактора, снаружи доступен только Caddy. Производственная конфигурация включает Secure cookie для HTTPS. Секреты S3 не попадают в браузерную сборку. Не выставляйте MinIO в интернет.

Обновление выполняется той же командой `up -d --build`; тома сохраняются. **`docker compose down -v` удаляет данные.** SQLite рассчитан на одну реплику API и локальный диск, не сетевую ФС. В этой версии нет совместного редактирования в реальном времени.

## Staging: автоматический деплой после merge

Домен staging: `https://sacura-test.duckdns.org`, VPS: `208.92.227.154`. Workflow `.github/workflows/verify.yml` запускает тесты и проверку контейнеров; затем только для `push` в `staging` (включая merge PR) запускает `deploy-staging`. Ручной запуск `workflow_dispatch` разрешает повторить деплой текущей `staging`. PR и другие ветки запускают проверки без деплоя. Одновременно выполняется один деплой; предыдущий запущенный деплой не прерывается.

GitHub Environment `staging` содержит `STAGING_SSH_KEY` и должен содержать `STAGING_KNOWN_HOSTS` с подтверждённым ключом сервера. Переменные окружения: `STAGING_HOST=208.92.227.154`, `STAGING_PORT=22`, `STAGING_USER=sacura-deploy`. Пароль root не хранится в GitHub и не используется CI. SSH проверяет host key строго; workflow не использует `StrictHostKeyChecking=no` или непроверенный `ssh-keyscan`.

Первичная подготовка Ubuntu после установки Docker: передать **публичный** ключ деплоя и выполнить от root:

```sh
bash engine-web-prototype/deploy/bootstrap-staging.sh /tmp/sacura-staging.pub EMAIL_ДЛЯ_ACME
```

Скрипт создаёт `sacura-deploy`, добавляет его в группу Docker, устанавливает ключ без forwarding/PTY и готовит `/opt/sacura/staging/shared/.env` со случайным S3-секретом. Существующий `.env` не перезаписывается. Доступ к Docker позволяет управлять контейнерами и хостом; ключ доступен только окружению staging. Перед первым деплоем проверьте DNS и свободные 80/443 на VPS.

Релизы находятся в `/opt/sacura/staging/releases/<полный-SHA>/engine-web-prototype`, рабочий — по ссылке `/opt/sacura/staging/current`. Данные лежат в постоянных Docker-томах проекта `sacura-staging`, `.env` находится вне релизов. Клиент и API получают теги образов по SHA. Сначала собираются образы, затем создаётся снимок БД и обновляются контейнеры. После проверки публичного HTTPS, API и точного SHA в `/version.json` переключается ссылка `current`. Если запуск или проверка не удались, скрипт пытается вернуть контейнеры предыдущего релиза. Это не откатывает миграции базы: изменения схемы должны сохранять совместимость с предыдущим релизом.

В футере **главного меню** показывается `v<версия package.json> · staging · <короткий-SHA>`. В редакторе версия не отображается. `/version.json` содержит полный SHA для автоматической проверки. Старые релизы и образы автоматически не удаляются; перед очисткой сохраняйте рабочий и предыдущий релиз, а также согласованный бэкап БД и моделей.

## Внешний S3 / AWS

Создайте приватный бакет у провайдера, задайте `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT=https://адрес-провайдера`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_CREATE_BUCKET=false`. Для AWS обычно используйте `S3_FORCE_PATH_STYLE=false`; для S3-совместимого провайдера — согласно его требованиям. API использует [AWS SDK v3](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/javascript_s3_code_examples.html). Текущий Compose продолжит запускать локальный MinIO, но API будет обращаться к внешнему endpoint.

Учётной записи нужны `s3:ListBucket` на бакет (проверка доступности), `s3:GetObject` и `s3:PutObject` на `meshes/*`. Локальный MinIO собирается из исходников официального [релиза 2025-10-15](https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z): готовые upstream-образы недоступны, а репозиторий архивирован. Первая сборка скачивает Go-зависимости и может занять несколько минут. Перед публичным размещением выберите поддерживаемое S3-хранилище. Для локального MinIO бакет создаётся автоматически при `S3_CREATE_BUCKET=true`. Включите версионирование и резервирование бакета у провайдера. Не удаляйте S3-объекты, пока на них ссылаются проекты или их предыдущие версии: автоматическая сборка неиспользуемых моделей пока не выполняется.

## Резервные копии и восстановление

Согласованный снимок SQLite, включая текущие изменения WAL:

```sh
docker compose exec -T api node backup.js
```

Команда напечатает путь `/data/backups/projects-...sqlite`. Скопируйте его на отдельный носитель:

```sh
docker compose cp api:/data/backups/ИМЯ_СНИМКА.sqlite ./projects-backup.sqlite
```

Для production добавляйте `-f compose.yaml -f compose.production.yaml` к командам Compose. Для полного бэкапа остановите входящие записи (`docker compose stop web`), сделайте снимок SQLite, затем остановите MinIO и сохраните Docker-том `sacura_meshes` средствами резервирования томов. Верните `minio` и `web` через `docker compose start minio web`. При внешнем S3 сохраните бакет `meshes/` средствами провайдера. Бэкап одной БД не содержит мешей. Храните БД и бакет вместе, вне VPS.

Для восстановления остановите стек, восстановите том S3 и `projects.sqlite` в томе проектов; удалите старые `projects.sqlite-wal` и `projects.sqlite-shm`, восстановите владельца файла UID/GID 1000 (пользователь `node`) и запустите стек. Не копируйте поверх открытой SQLite-БД. Перед публикацией проверьте восстановление на отдельной инсталляции.

## Диагностика и разработка

```sh
docker compose logs --tail=100 api web minio
npm ci --prefix server
npm test --prefix server
npm test --prefix frontend
npm run build --prefix frontend
```

Healthcheck API проверяет SQLite и доступность S3. Nginx ограничивает частоту API-запросов и размеры загрузок. SQLite использует WAL, параметризованные запросы и атомарную проверку версии. Сбой S3 не подтверждает сохранение JSON со сломанными ссылками.

Для разработки с API без контейнеров используйте Node.js 24+, передайте переменные из `.env` и `DB_PATH` с локальным путём, запустите `npm start` в `server`, затем `VITE_SERVER_STORAGE=true npm run dev` в `frontend`. Vite проксирует `/api` на `127.0.0.1:3000`; браузер может запросить авторизацию при первом обращении к API.

CI в `ci/action.yml` (запускается корневым `.github/workflows/verify.yml`) запускает тесты, production-сборку и Docker Compose с реальным MinIO. Smoke-проверка использует настоящий клиентский код сохранения, открытия и переносимого экспорта: проверяет OBJ, GLB с анимацией, дедупликацию, лимит 3 МБ, отказ для повреждённого GLB и изоляцию аккаунтов. После перезапуска повторно проверяются сессия, проекты, геометрия, анимация и экспорт. Проверку контейнеров можно повторить командой `node deploy/smoke.mjs` после установки npm-зависимостей фронтенда: она создаёт тестовые аккаунты по приглашениям и проекты, поэтому запускайте её на отдельной тестовой инсталляции. Перед запуском передайте `SACURA_SMOKE_LOGIN` и `SACURA_SMOKE_PASSWORD` существующего тестового аккаунта (или экспортированные `APP_USER`/`APP_PASSWORD`). Для проверки сохранности задайте `SACURA_SMOKE_STATE=/tmp/sacura-smoke-state.json` при первом запуске и повторите с тем же файлом после перезапуска. Файл содержит cookie тестовой сессии; удалите его после проверки. Другой адрес задаётся через `SACURA_SMOKE_URL`.


## Регистрация по приглашению

Любой вошедший пользователь создаёт приглашение из главного меню. Ссылка `/register?invite=…` действует 72 часа и используется один раз. Страница `/register` без токена объясняет необходимость приглашения; публичного перехода к регистрации нет. После регистрации сохраняется автоматический вход и открывается главное меню. Если ссылка открыта в уже авторизованном браузере, показывается сообщение о текущем аккаунте, приглашение остаётся неиспользованным.

API:

- `POST /api/invites` — требует session cookie, возвращает только `url` и `expiresAt`.
- `POST /api/invites/validate` с `{invite}` — публичная проверка, возвращает только `expiresAt` либо ошибку для некорректного, истёкшего или использованного приглашения.
- `POST /api/auth/register` — прежний endpoint, теперь обязательно принимает `{login,password,invite}`. Без действующего приглашения ответ 403; вошедшему пользователю — 409.
- Вход, выход и проверка сессии остаются на `/api/auth/login`, `/api/auth/logout`, `/api/auth`.

Миграция `server/migrations/001-invites.sql` добавляет `invites` (SHA-256 хеш токена, создатель, время создания/истечения/использования, зарегистрированный пользователь) и `auth_rate_limits`. Она применяется автоматически и повторяемо при запуске API, в соответствии с существующими startup-миграциями. Старые пользователи, пароли, проекты и сессии сохраняются. Отдельная миграционная CLI-команда не нужна:

```sh
docker compose up -d --build
# Без Docker, после настройки существующих S3/DB переменных:
npm start --prefix server
```

При production-запуске используйте существующие `-f compose.yaml -f compose.production.yaml`. API-образ включает каталог миграций. Регистрация и погашение приглашения выполняются вместе в `BEGIN IMMEDIATE`; проверка срока и использования повторяется внутри транзакции после вычисления scrypt. Занятый логин не погашает приглашение.

Новых обязательных переменных нет. Необязательный `FRONTEND_BASE_URL=https://editor.example.com` задаёт канонический frontend origin; иначе URL строится по request Host, а схема определяется существующим `COOKIE_SECURE`. Для Vite с API отдельная настройка не нужна: proxy сохраняет Host браузера. Первый аккаунт на пустой БД создаётся только серверной конфигурацией `APP_USER`/`APP_PASSWORD`, без публичного bootstrap endpoint и без административной роли.

Лимиты хранятся в SQLite и сохраняются после перезапуска: вход — 5 запросов/минуту/IP, регистрация — 3/час/IP, проверка приглашений — 30/минуту/IP, создание — 10/час/пользователь. Ответ 429 содержит `Retry-After`; блокировка прекращается после окна. Это общий бюджет запросов, включая успешные попытки. Приложение рассчитано на существующую одну реплику API.

Прямой Node-запуск по умолчанию не доверяет `X-Forwarded-For`. Compose задаёт `TRUST_PROXY=1`, поскольку API не публикует порт, а Nginx **перезаписывает** forwarded IP адресом проверенного клиента. Не выставляйте API напрямую с этой настройкой. В production Caddy имеет адрес `172.29.251.2` в отдельной сети `172.29.251.0/24`; только этому адресу Nginx доверяет для real IP. При конфликте подсети измените её в `compose.production.yaml` и соответствующий `set_real_ip_from` в `frontend/nginx.conf` вместе. Caddy не доверяет внешним forwarded-заголовкам по умолчанию. Токен проверки передаётся в JSON, а не в URL API. Nginx access log записывает только путь без query и Referer; error log для `/register` отключён, чтобы не записывать секрет из request line; `Referrer-Policy: no-referrer` предотвращает передачу invite URL в Referer.

Локальная ручная проверка: войдите, создайте приглашение в главном меню, нажмите «Копировать ссылку», откройте её в приватном окне и зарегистрируйтесь. Повторное открытие ссылки в приватном окне должно показать ошибку. Проверьте также `/register` без параметра, неправильный токен и открытие ссылки в исходном авторизованном окне. Для разработки frontend запускайте с `VITE_SERVER_STORAGE=true npm run dev --prefix frontend`; без этого флага остаётся локальный прототип без серверных аккаунтов.

Основные изменения: `server/auth.js`, `app.js`, `index.js`, SQL-миграция и backend-тесты; `frontend/src/AuthGate.jsx`, `ProjectHome.jsx`, `InviteDialog.jsx`, `invites.js`, общая оболочка `Dialog.jsx` для существующего `ProjectDialog.jsx`, CSS и DOM-тесты; Dockerfile API, Nginx, Compose, `.env.example`, deployment smoke и CI. Для DOM-тестов добавлены devDependencies `jsdom` и `@testing-library/react`.

Проверки из `engine-web-prototype`:

```sh
npm test --prefix server
npm test --prefix frontend
VITE_SERVER_STORAGE=true npm run build --prefix frontend
```

В проекте нет отдельных lint/typecheck scripts: используется JavaScript/JSX, JSX проверяется Vite-сборкой, поведение — Node/DOM-тестами.
