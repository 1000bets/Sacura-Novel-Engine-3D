## Исправленные интеграционные дефекты

- Экспорт находил аудио преимущественно в Event Actions и пропускал ссылки функций/механик и относительные ресурсы. Обход расширен на авторские данные; перенос ресурсов использует существующий codec, включая вложенные ресурсы glTF. Стандартная музыка без assetId также упаковывается. Совпадение имени Event с названием аудио больше не включает посторонний файл. Ресурс с неподдерживаемыми внешними GLB-зависимостями даёт ошибку до выпуска HTML.
- Холодная загрузка сохранения в player и кнопке виджета Editor сначала запускала проект и повторяла стартовые действия. Теперь данные проверяются и восстанавливаются без start/initialize/входных событий. Неверное сохранение не останавливает действующий сеанс.
- Прямые асинхронные операции и функции не всегда учитывались при Save. Учтены существующие flights и inputFlights; Promise не сериализуется. Сохранены принадлежность статических эффектов и held-состояния Event, чтобы последующая очистка и перенос между сценами работали.
- Старый фасад мог обратиться к миру нового запуска. Доступы защищены поколением сеанса; контексты проверяют сцену и владельца после await. Dispose модуля снимает его подписки/handles синхронно; ошибки очистки изолированы и записываются.
- Ошибка одного условия могла подавить последующие правила того же сигнала. Теперь следующий допустимый запуск проверяется. Присваивание Blueprint глобальной переменной проверяет её объявленный тип до изменения.
- Новые таймеры/двери/взаимодействия теперь создают канонические правила с действиями. В совместимом чтении старой формы остаётся один исполнитель. Источник таймера проекта/сцены указан явно, без подстановки героя.
- Создание нового проекта из шаблона добавляло пять стартовых Events при каждом переносе. Свежий получатель теперь получает только Events пакета; импорт в существующий проект сохраняет его содержимое.
- Добавлен ограниченный журнал фактического исполнения и исправлена сводка действий, показывавшая `[object Object]`. Запись stop больше не заслоняет последний сигнал механики без отдельного ruleId.

## Сохранение и восстановление

Безопасная точка: запущенный готовый сеанс в PLAYING, WAITING_INPUT, WAITING_OBJECT, WAITING_CHOICE либо ENDING, когда очереди правил пусты и нет выполняющихся Event, функций, операций и обработчиков ввода. Paused-held статические эффекты допустимы; пауза незавершённого асинхронного действия не делает Save безопасным. Отказ содержит причину, данные проекта не меняются.

Восстанавливаются глобальные и локальные переменные экземпляров, FSM, инвентари/экипировка владельцев, здоровье/боезапас подключённых возможностей, ресурсы, тела, таймеры с остатком игрового времени, cooldown/once, история/выборы, статические эффекты и held-метаданные их владельцев. Таймеры используют общий игровой clock и не идут на паузе. Загрузка возобновляет игру; стартовые награды, подборы и входные события не переисполняются. Журнал не является состоянием прохождения и не сохраняется.

V2 требует тот же projectId и совместимый отпечаток авторской логики, данных, виджетов, подключённых модулей с версиями/порядком и используемых контрактов операций. Название проекта и оформление/комментарии узлов графа можно менять; изменения логики требуют нового сеанса или исходной версии проекта. Отпечаток — проверка совместимости, не криптографическая гарантия безопасности. V1 читается после структурной проверки существующих ссылок/типов с сообщением, что версия исходной логики неизвестна. Восстановление произвольного старого состояния после рефакторинга не обещается.

Ограничения: незавершённое выполнение не восстанавливается; Promise, внешние handles, позиция потокового аудио и курсор анимации не сериализуются. Статические эффекты восстанавливаются без аудио. Legacy gate сохраняет данные проверки, но его timeout-подсказка не перевзводится автоматически после загрузки. Изменение числа/ID объектов или структуры виджета может консервативно отклонить V2 Save. Это явный отказ до замены сеанса, без частичной загрузки.

## Журнал и жизненный цикл

Кольцо содержит максимум 128 записей; отдельные значения также ограничены по глубине/длине. Записываются публикация сигнала с источником/целью, совпадение области/фильтра и причины отказа, реально прочитанные значения условий, запуск/результат/ошибка действия, once/cooldown/reentry, переход/отмена/цикл/cleanup. Ссылки открывают существующий объект, Event или граф. Свёрнутая диагностика объясняет последний проверенный запуск выбранной механики. Пассивный счётчик без собственного правила не получает выдуманную историю: проверяется таймер или другое правило, изменяющее его.

Порядок — FIFO публикаций, порядок правил в snapshot; значения условий фиксируются при публикации до нескольких await. Состояние обновляется до сигнала о нём. FSM применяет первый допустимый переход соответствующей ревизии и отменяет действия покидаемого состояния. Очередь: 128 сигналов/ожидающих запусков, максимум 8 активных запусков, 16 ожидающих на правило, цепочка до 32; дополнительно обнаруживается повтор правила в cause chain. Значение maxRuns по умолчанию 1. Параллельность действий использует Event runtime. Движение/физика обновляются системами, каждый кадр в журнал не пишется. Детерминизм физики между платформами не заявляется.

Stop/restart, выход из сцены и удаление владельца инвалидируют контексты. Старое завершение не меняет новый мир. Доверенное расширение обязано вызывать assertActive перед изменением после своего await и снимать внешние подписки в dispose: произвольный код расширения не является sandbox.

## Добавить доверенный модуль движка

1. Создать модуль по образцу `src/capabilities/turns.js`. В `registerCapability` указать стабильный ID/версию, data с parameters/stateSchema/scopes, операции с схемами результата, сигналы с payloadSchema и редакторские названия.
2. Реализовать initialize/update/enter/sync по необходимости, validateProject/validateSavedState и bindings. Обновлять состояние владельца/экземпляра и публиковать сигнал после изменения. Использовать игровой dt; cleanup обслуживает удалённых владельцев, dispose синхронно снимает собственные handles при остановке.
3. Добавить один import в `gameCapabilities.js`, общий для Play/player. Не менять список GameplayWorkspace или центральный switch. Новые поля появляются из общей схемы. Проверить headless исполнение/сохранение и обе сборки.

Авторский пакет содержит только определения/вызовы этих возможностей и требования к ним. Импорт JSON не регистрирует исполняемый код, не вызывает eval/Function/dynamic import и не скачивает неизвестные расширения.

## Создать пользовательскую механику

В механиках выбрать владельца, открыть библиотеку и добавить готовую возможность либо создать своё определение. Назвать заготовку, открыть нужные типизированные параметры, собрать «Когда / Если / Сделать / Иначе». Сложную часть открыть как существующую Blueprint-функцию. Применить определение к другой двери/сцене/проекту и выбрать свои объекты; значения и состояние экземпляра независимы. «Изменить логику» относится к общему определению, «Создать копию» создаёт независимый вариант.

Для передачи выбрать Event, функцию, механику или шаблон → Экспортировать → проверить состав и найденные внешние привязки → скачать пакет. Получатель: Импортировать → preview/диагностика → выбрать свои объекты/переменные → добавить копию одним Undo. Повторный импорт не обновляет имеющиеся данные автоматически. Автор/источник сохраняются при редактировании и повторном экспорте. Полный цикл офлайн; магазин, оплата, аккаунты и cloud-sync не требуются.

## Миграция и остаточные жанровые имена

Gameplay v1 читается с резервным source/отчётом, переводится в v2 идемпотентно, ID/правки/Events/функции/Input/HUD сохраняются. Непереносимые поля перечисляются в отчёте; неизвестные данные/определения не удаляются молча. Неизвестная возможность блокирует исполнение с диагностикой, а не устанавливается из пакета. Старая совместимость переводит реакции смерти/счёта/победы в явные правила, не запускает второй обработчик.

В GameSession/runtime/RuleRuntime/GamePlayer/play/WidgetWorkspace нет runtime-ветки по fps/shooter/playerId. Остатки: `gameplayModel` — deprecated поле, legacyCamera/applyGamePreset и v1 validation; `capabilityMigration` — назначение прежнего героя явно владельцам/целям/HUD при переходе v1; `gameplayMigration` — отчёт/metadata; `gameplayAuthoring` — совместимый рецепт FPS; каталог/гайд — обучение шутеру из шаблона; `mechanicPackages` — remap старых ссылок. fps у animationThumbnails означает частоту кадров. Эти адаптеры ещё нужны старым данным и удаляются после перевода потребителей, не являются требованиями нового проекта.

Продуктовые принципы соблюдены в проверенных пределах: основной путь использует названия/выбор и короткие параметры без JSON/ID; отдельная редактируемая логика проходит A→B→C без A; новые UI-механики работают без героя/HP/оружия. Проверены перечисленные возможности, а новые базовые возможности добавляются доверенным модулем. Полная поддержка любого жанра без программирования не заявляется.
