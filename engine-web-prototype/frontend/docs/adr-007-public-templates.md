# ADR-007: встроенные шаблоны и завершение gameplay.version 1

Дата: 13–14 октября 2026 года. Ветка `feature/new-ui-fix`.
Статус: реализовано в рабочей копии. Основание —
[обязательные требования](../../../docs/PRODUCT-REQUIREMENTS.md).

## Исходное состояние и решение

В актуальных shooter/point-and-click JSON был `sacura-project-template` v1 и
`gameplay.version: 1`: preset/playerId, legacy правила с отдельными полями действий,
неявные владельцы оружия/инвентаря, AI без явно назначенной цели. Читатель добавлял
правила совместимости и мосты HUD. Функция award-kill сравнивала ID с
`shooter-hero`, HUD/меню говорили о пяти целях. В квесте были лишние здоровье и
боевые переменные. Исходный набор проходил 515/515; эти данные сохранены целиком
в `tests/fixtures/legacy-*.sacura-template.json`.

Новые файлы используют авторский контейнер formatVersion 2, roots.kind template,
gameplay.version 2. Версия формата не является версией проекта или механики.
`builtinTemplates` содержит только каталог/описания/пути. `loadBuiltinTemplate`
проверяет пакет. `authoringTemplates.instantiateAuthoringTemplate` создаёт пустой
проект и применяет тот же план импорта 5А, что пользовательский пакет. Создание
доступно из ProjectHome и диалога нового проекта. Файлы пакетов также читаются
обычным файловым путём; импортированные пакеты шаблона остаются в локальной
библиотеке. Старый контейнер читается совместимым адаптером.

ID шаблона не выбирает runtime или скрытую редакторскую реализацию. После импорта
используются только объекты, native возможности, Input Actions, камеры, виджеты,
механики, функции и правила проекта. Новых ECS, языка или планировщика нет.

## Четыре настоящих примера

| Пример | Общая логика | Фактическая проверка |
| --- | --- | --- |
| Новелла | Event ответа → сигнал награды → общая функция → resource.add; typed stateBinding отношения и native availability следующего ответа | Поддержка открывает личный вопрос, холодный ответ оставляет его недоступным; headless и standalone-браузер |
| Point & click | Native инвентарь/рецепт; условие itemCount, правило двери, Event открытия/перехода истории | Запертая дверь не открывается без ключа; с ключом открывается диалог. Headless и полный браузерный путь ключ + записка + дверь |
| Шутер | Раздельные движение/камера/здоровье/оружие/инвентарь; явные death/hit/pickup правила; награда и FSM задания | 3 и 8 переименованных целей после повторного пакования; движение, выстрел, перезарядка, счёт, финал. Отдельно проверена цель вне группы награды. Браузер: два выстрела, 1 цель/100 очков, урон и Game Over |
| UI-кликер | Конкретная кнопка → сигнал награды; variable.set скорости; общий игровой tick → resource.add | Монеты, улучшение и таймер; save/restore. В standalone работают кнопки и растущий ресурс; объектов, героя, HP и оружия нет |

«Награда за действие» — обычное определение с параметрами владельца, счётчика и
величины. Оно вызывает **одну** Blueprint-функцию с зарегистрированной
`sacura.resource.add`, сохраняет граф/комментарий и переносится как
`reward.sacura-package.json`. Та же функция используется в трёх примерах.
Её можно вызывать из обычного правила/Event по сигнатуре; код ядра не меняется.
Рецепт импортируется в существующую сцену с preview, выбранной привязкой,
переименованиями и одним undo; существующие ввод, камера и UI сохранены.

## Смерть, награда и цель задания

Health изменяет состояние перед сигналами hit/death. Правила шутера явно
отключают возможности, скрывают побеждённую цель, записывают результат, начисляют
награду и отправляют сигнал награды. Отдельное правило сигнала смерти запрашивает
проверку выбранных целей независимо от фильтра награды; смена цели не требует
изменения этого обработчика. Герой имеет отдельное правило, Event смерти и
Game Over; он не входит в группу награды. Лечение вызывает зарегистрированную
операцию инвентаря только при ранении/наличии предмета. HP, ammo/reserve, medkits,
score/kills привязаны к конкретным возможностям/владельцам; обновление этих имён
не является обязательным поведением ядра.

FSM задания: waiting → active по явному сигналу Event начала боя; active → complete
по сигналу проверки и `sacura.health.all-dead` для выбранной коллекции/тега.
Проверка пустой коллекции возвращает false. Пока задание не началось, проверка
не завершает его. Состав активных объектов с тегом вычисляется заново на снимке
публикации сигнала; новые живые участники блокируют завершение. Скрытые участники
учитываются; active=false исключает объект. Отсутствующее здоровье не трактуется
как смерть. Health один раз инициализирует поздно добавленную возможность, не
сбрасывая существующие HP или dead. После complete новых переходов нет;
новый сеанс запускает задание заново. Число пять осталось только количеством
объектов исходного примера, не условием/строкой счётчика.

## Миграция

`gameplayMigration.finalizeGameplayMigration` завершает существующий
`migrateCapabilities`: сохраняет ID и native карты возможностей, переводит
legacy действия в canonical actions/otherwise, сохраняет ожидания и источник
времени, переносит objectId в filter там, где это ссылка на участника сигнала.
У таймеров/областей subject binding остаётся для native генератора. Связи
с Event/функцией и параметры сохраняются; известный callback получает явно
передаваемый объект своего native сигнала. Функции и оформление графов исходного
проекта не переписываются. Preset больше не исполняется после преобразования.

Контроллер использует ownerId; playerId остаётся устаревшими сведениями для
совместимости, не выбирается редактором и не служит источником управления в v2.
Readonly legacy views и команды нужны для прежних Events/сохранений; это не
второй обработчик правил. Существующие map/recordId адаптеры механик показывают
те же определения, а не хранят вторую конфигурацию здоровья или оружия.
Повторное чтение v2 не дописывает compatibility rules/bindings/resources.
Удалённые автором реакции совместимости не восстанавливаются.

`project.gameplayMigration` содержит отчёт и первоначальный source. Неизвестные
настройки/версии сохраняются с диагностикой, отсутствующие владельцы требуют
проверки. Отчёт доступен в существующих дополнительных свойствах проекта,
исходник скачивается отдельной кнопкой. Backup исключён из авторского пакета,
копии runtime и player HTML; оригинал остаётся в редакторе/сохранённом проекте.
Данные не записываются поверх исходного файла автоматически. Старые saves
адаптируются прежним `adaptSavedCapabilities`; события входа не переигрываются.

## Исправленные разрывы потребителей

- Package remapper теперь переносит elementId фильтра кнопки, defaultCameraId
  сцены и ui назначения виджетов. Проверяется фактическое соответствие новым ID.
- Ключи project.variables не переназначаются как ID объектов/ресурсов. Имя
  переменной coins/relationship может совпадать с ID ресурса, оставаясь именем.
- Шаблон без реплик использует одну пустую принимающую сцену; не оставляет лишнюю
  сцену получателя. Общая рабочая область выбирает существующую механику при
  открытии другого проекта и не сообщает о пустом проекте при наличии механик. При создании нового проекта поставляемые шаблоном виды
  виджетов заменяют стартовые fallback меню получателя, не оставляя дублей;
  применение рецепта к существующему проекту сохраняет его виджеты.
- RuleFields выбирает конкретную кнопку по имени, включая elementId. Удалённая
  кнопка диагностируется. История и ввод используют общий ruleMatches для
  взаимодействия, включая проект без героя; посторонний объект не поглощает
  щелчок только из-за наличия где-то правила двери.
- Копия проекта переназначает project references в виджетах/Events/функциях,
  сохраняя исторический backup без правок.
- Inventory предоставляет typed binding количества конкретного предмета.
  Камера принимает реальные источники ввода мыши/геймпада; шаблон передаёт источник
  из контекста, а не притворяется мышью для любого устройства.

## Проверки и воспроизведение

Из frontend выполнить `npm test`, `npm run build:player`, `npm run build`.
Дополнительный `node scripts/export-template-players.mjs` создаёт четыре настоящих
HTML с собранным player в `dist/examples`. Изменение авторских данных пересобирается
обычным экспортом; для сопровождения встроенных JSON есть
`scripts/build-builtin-templates.mjs`, который не вызывается при импорте/запуске.

Новые headless проверки в `universal-templates.test.js`: пакетный путь всех четырёх
примеров, новый проект/ID remap, экспорт/повторный импорт, сборка HTML с настоящим
player, новелла и оба ответа, дверь с ключом, 3/8 целей, пустая группа, pre-start,
новая цель и terminal state, смена целей независимо от группы награды, UI-кликер/save, награда в двух принимающих жанрах,
preview/undo без перезаписи, исходник и идемпотентность миграции, аптечка/смерть/save,
обычный ввод без героя. Новые UI-тесты проверяют кнопку-фильтр и отчёт миграции.

Legacy characterization и прежние genre-тесты читают замороженные исходные
шаблоны и проверяют прежние наблюдаемые результаты после миграции. Это не моки
новых примеров: их собственные tests читают новые public пакеты и запускают runtime.
Старые assertions отдельных legacy полей теперь проверяют signal/actions;
проверки счёта, смерти, переходов, остановки и сохранений не ослаблены.

Итоговый `npm test`: 532/532. Обе сборки прошли; build предупреждает о чанках
>500 kB. Браузерный прогон standalone на 1366×768 выполнил кнопки кликера,
поддержку/личный ответ новеллы, подбор/рецепт/дверь квеста, старт/выстрел/награду/
урон/Game Over шутера. Фиксируются настоящие снимки:
[новелла](screenshots/template-novel-player.jpg),
[квест](screenshots/template-quest-player.jpg),
[шутер](screenshots/template-shooter-player.jpg),
[кликер](screenshots/template-clicker-player.jpg).
В браузерном редакторе проверены создание кликера из каталога, выбор конкретной
кнопки без дублей меню и одна сцена. Ширина document/viewport — 1366/1366, высота
768; консоль этой проверки без error/warn. Старый шутер импортирован через файл,
отчёт раскрыт, скачанный backup JSON сравнен с исходным fixture — данные совпали.
Дополнительные снимки: [редактор](screenshots/template-clicker-editor.jpg),
[отчёт](screenshots/template-migration-report.jpg).
Полное завершение 3/8 целей подтверждено headless, не ручным браузерным прогоном.

## Файлы и границы

Данные: четыре `public/game-templates/*.sacura-template.json`, новый
`reward.sacura-package.json`, их README. JS: `builtinTemplates`, `authoringTemplates`
(новый), `gameplayMigration` (новый), `gameplayModel`, `capabilityMigration`,
`mechanicsModel`, `mechanicPackages`, `packageReferences`, `projectLifecycle`,
`runtime`, `gameExport`, `ruleModel`, capabilities `health`, `inventory`, `camera`.
React: `ProjectHome`, `Editor`, `GamePlayer`, `GameplayWorkspace`, `MechanicFields`,
`MechanicProjectProperties`, `GameplayMigrationReport` (новый).
Legacy API: `gameplayAuthoring`. Scripts: два новых генератора/экспортера выше.
Тесты: новый `universal-templates`, `mechanics-ui`, сохранённые fixtures и адаптация
`genre-templates`, `gameplay-characterization`, `gameplay-authoring`, `capabilities`,
`operation-model`, `package-exchange`, `mechanics`. Документация: этот ADR,
`gameplay-unification`, frontend README и инструкции примеров.

Простота: готовый пример создаётся из каталога, его цели/награда/кнопки меняются
в обычных формах. Переносимость: одна упаковка, dependency closure, новые ID,
preview/undo и offline HTML; авторский оригинал сохраняется. Универсальность:
четыре жанра используют одну модель, обязательных hero/HP/weapon нет.

Не реализованы магазин, слияние обновлений, произвольные скриптовые расширения
из пакета, новый ECS или физический детерминизм. Поздние цели добавляются в
существующие данные объектов/возможностей; отдельный редактор спавнера не добавлен.
Неизвестные настройки не превращаются автоматически в поддерживаемые возможности.
Старый preset-builder API оставлен как совместимый сборщик обычных данных, без
входа в общую навигацию; новые примеры его не вызывают. Тестирование с пользователями,
все браузеры, устройства/геймпад, WebGL-платформы и отказы хранилища не проверялись.
Рабочие изменения пользователя сохранены; reset, commit и push не выполнялись.
