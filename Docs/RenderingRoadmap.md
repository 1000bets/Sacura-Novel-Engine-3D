# План развития рендера Sacura Novel Engine 3D

Текущее дополнение: минимальный Forward-путь по пунктам 1, 2 и 4–7 реализован в исходниках; детали и статус проверки находятся в `Docs/ForwardRenderer.md`. Анимация/GPU skinning исключены по запросу. Этот roadmap сохраняет дальнейшие расширения и не является протоколом успешно пройденной GPU-проверки.

Дата: 24 сентября 2026 года.

## Цель и границы

Создать законченный forward renderer для трёхмерной новеллы: статические и анимированные персонажи, материалы, освещение, тени, прозрачные поверхности, стабильная камера, постобработка и одинаковое изображение в Editor Game и SakuraPlayer. Qt принадлежит Engine и отвечает за runtime UI. Diligent остаётся графической основой; непосредственные вызовы GPU API выполняются только на Render Thread внутри приватного Rendering/RHI.

Состав зависимостей сохраняется: PhysX, DiligentFX, ozz, Python и существующие backend не удаляются и не заменяются. Deferred, ray tracing, виртуализированная геометрия и собственный аналог большого универсального render graph не входят в этот план.

Это план последующей реализации рендера, а не описание уже готовых возможностей. Изменения архитектуры текущего запроса отдельно описаны в `Docs/Implementation/Task-15.md`.

## Исходное состояние

- Renderer использует один графический pipeline, одну поверхность и TestMesh.hlsl. Результат — vertex color × base color × optional texture; свет и нормали пока не участвуют в шейдинге.
- Снимок сцены содержит меши, камеру и источники света. Загрузка мешей и текстур асинхронная, загрузка на GPU выполняется через очередь Render Thread.
- CPU-материал хранит больше сведений, чем использует renderer. Нет завершённых вариантов opaque/masked/blended материалов, системы освещения и теней.
- Есть загрузка скелетов и анимаций, но нет законченной цепочки sampling → pose → skinning → draw.
- После архитектурной правки Engine является единственным производителем кадров. Scene и Game используют общую native-поверхность с разным выбором мира и камеры. Это ещё не поддержка одновременных viewport.
- Qt StoryWidget общий для Game и Player. Сейчас это отдельная панель рядом с native viewport; композиция произвольного HUD поверх 3D требует отдельного проверенного решения.

## Порядок реализации

### Этап 0. Проверяемый контракт кадра и базовая сцена

Затронутые части: Engine, RenderThread, RenderFrameQueue, SceneExtractor, Qt host, тестовые приложения.

1. Собрать архитектурные изменения в Debug и прогнать native, Python и Qt-тесты. Проверить Editor ON и Editor OFF, включая запуск Player без Editor.
2. Добавить интеграционный тест: загрузка проекта → Play → Pause → Step → Stop → повторный Play → закрытие во время Play. Проверить игровой tick в Player и неизменность EditWorld.
3. Добавить техническую сцену с камерой, несколькими мешами, текстурами и светом. Сохранить фиксированные позиции и детерминированное состояние анимации для будущих сравнений изображения.
4. Измерять CPU время подготовки кадра, длину очереди, GPU время проходов, draw calls, число треугольников и расход GPU памяти. Зафиксировать GPU, драйвер, разрешение и конфигурацию сборки; производительность сравнивать на одной машине.
5. Проверить resize, DPI, сворачивание, закрытие окна и отказ инициализации backend. Состояние без камеры должно иметь понятную диагностику.

Критерий завершения: один логический кадр отправляется один раз, номера кадров возрастают, Game и Player используют игровую камеру, нет ошибок thread assertions и обращений к уничтоженным окнам.

### Этап 1. Поверхности, render targets и время жизни ресурсов

Затронутые части: Rendering/RHI, RenderView, RenderSurface, RenderFrameData, RenderThread, AssetGpuUploader.

1. Разделить GraphicsDevice и поверхность представления: один device, несколько независимых swapchain или offscreen targets. Описывать каждый вид через ViewId, SurfaceId, размеры и камеру.
2. Передавать набор видов в одном пакете кадра. Editor не создаёт конкурирующие frame producers. Рендерить каждый вид с его world snapshot и камерой.
3. Ввести HDR scene color и depth targets на каждый вид, пересоздаваемые при изменении размера. У view должны быть собственные ресурсы истории для будущих temporal effects.
4. Реализовать retirement ресурсов после завершения GPU-работы. Освобождение mesh/texture и resize не должны уничтожать ресурсы, ещё используемые кадром.
5. Дать GPU-идентификаторам поколение или привязку к device epoch. После пересоздания device старые идентификаторы не могут случайно указывать на новые ресурсы. Повторная загрузка берёт данные из CPU-ресурсов.
6. Выбрать и проверить композицию Qt HUD с native viewport: порядок слоёв, ввод, DPI, fullscreen и снимки экрана. Qt не получает Diligent immediate context и не выполняет команды renderer на GUI thread.

Критерий завершения: два viewport одновременно показывают разные камеры; resize одного не меняет второй; закрытие поверхности и повторное создание не дают stale handles, утечек и ошибок validation layer.

### Этап 2. Материалы, текстуры и цветовой pipeline

Затронутые части: MaterialResource, TextureResource, SceneAssetResolver, RenderObject, GPU material cache, HLSL.

1. Заменить TestMesh pipeline на явно выбранный тип материала: Unlit и Lit metallic/roughness. Поддержать base color, metallic, roughness, normal, emissive и occlusion.
2. Определить цветовое пространство каждой текстуры: цветовые карты декодируются как sRGB, normal/roughness/metallic остаются линейными данными. Освещение и HDR-композиция выполняются в линейном пространстве.
3. Добавить tangent basis и нормальную матрицу для non-uniform scale. Проверить зеркальные UV, отрицательный scale и double-sided материалы.
4. Добавить mipmaps, sampler settings, fallback textures и явную политику отсутствующих карт. Ошибка загрузки не должна оставлять текстуру от предыдущего материала.
5. Ввести GPU-материалы и кэш pipeline/resource bindings по описанию материала. Хранить постоянные параметры отдельно от per-object constants.
6. На выходе выполнить одну явную тональную компрессию и корректное преобразование в формат swapchain; исключить двойное применение gamma.

Критерий завершения: тестовые поверхности предсказуемо меняют шероховатость и металличность; normal map ориентирована правильно; одинаковая сцена имеет сопоставимое изображение на D3D12 и Vulkan.

### Этап 3. Освещение и окружение

Затронутые части: LightComponent, SceneExtractor, RenderLight, frame/view buffers и lighting shaders.

1. Реализовать directional, point и spot light с определёнными единицами, затуханием и ограничением радиуса.
2. Подключить освещение к Lit-материалам. Согласовать BRDF, normal maps и emissive с цветовым pipeline этапа 2.
3. Добавить environment map, diffuse irradiance, specular prefilter и BRDF LUT для IBL. Подготовка карт окружения должна быть воспроизводимой.
4. Начать с простого ограниченного списка источников на view. Предел должен быть явным, а превышение — диагностироваться. Forward+ вводить после измерения реальной стоимости источников.
5. Поддержать выключение света, изменение параметров и удаление источников без сохранения устаревших GPU-данных.

Критерий завершения: каждый тип света влияет на сцену согласно своим параметрам; отключение всех источников оставляет только намеренно заданные environment/emissive составляющие.

### Этап 4. Тени

1. Реализовать shadow pass и atlas allocation с явным лимитом памяти.
2. Сначала добавить directional shadow с cascades и стабилизацией при движении камеры, затем spot shadows. Point shadows включать отдельным подэтапом из-за стоимости нескольких направлений.
3. Настроить depth bias и normal bias относительно масштаба сцены; добавить фильтрацию и контроль разрешения.
4. Учитывать alpha mask, double-sided материалы и деформацию скелета в shadow pass.
5. Добавить debug views глубины, каскадов и занятости atlas.

Критерий завершения: тесты тонких поверхностей, контактов, анимированного персонажа и движущейся камеры не показывают систематических артефактов acne, оторванных или нестабильных теней.

### Этап 5. Прозрачность и структура проходов

1. Разделить opaque, alpha-tested и alpha-blended draw lists. Явно задавать blend/depth-write/cull состояния.
2. Сортировать blended геометрию по принятой политике. Документировать ограничения пересекающихся прозрачных поверхностей; не обещать произвольную order-independent transparency в первой версии.
3. Использовать последовательность проходов: shadows → opaque/masked → sky → transparency → post-processing → presentation. Depth prepass добавлять по измеренной необходимости.
4. Отделить описание проходов и их входов/выходов от конкретных вызовов Diligent. Начать с простого списка зависимостей ресурсов и переходов состояний.
5. Подключить editor overlays отдельно от игрового изображения: выделение, gizmos и debug drawing не должны попадать в Player.

Критерий завершения: волосы/листва с mask, полупрозрачное стекло и непрозрачные поверхности взаимодействуют с depth и светом по заявленной модели. Переключение материала не наследует состояние предыдущего draw.

### Этап 6. Анимированные персонажи

Затронутые части: SkeletalLoader, gameplay animation components, ozz runtime, SceneExtractor, skinning shader.

1. Построить путь sampling и blending позы через ozz, затем local-to-model matrices и skinning palette.
2. Передавать снимок позы или GPU palette в render packet без указателей на изменяемые игровые объекты.
3. Реализовать GPU skinning позиций, нормалей и tangents. Использовать тот же deformation path в цветном и теневом проходах.
4. Обновлять bounds анимированного объекта для culling. Проверить root motion и иерархию отдельно от деформации.
5. Явно отклонять неподдерживаемые animation interpolation/morph варианты либо реализовать их; не терять такие данные молча.

Критерий завершения: персонаж воспроизводит клип и blend двух клипов, сохраняет корректные тени и не исчезает из-за bounds при движении конечностей. Pause/Step совпадают в runtime и редакторе.

### Этап 7. Постобработка и стабильность изображения

1. Ввести exposure и tone mapping, затем bloom и выбранный метод anti-aliasing.
2. Для TAA сначала добавить velocity, previous transforms, jitter и правила сброса истории при camera cut, resize и смене мира. Не подключать TAA к кадру без необходимых данных.
3. По требованиям сцены добавить SSAO, depth of field и цветокоррекцию. SSR и прочие эффекты оценивать отдельно по качеству и стоимости.
4. Интегрировать подходящие компоненты уже подключённого DiligentFX через RHI-адаптеры, проверяя API именно закреплённой в проекте версии.
5. Qt UI сохраняет резкость и читаемость: игровой текст не должен случайно проходить через 3D motion blur или TAA.

Критерий завершения: контролируемые сцены с движением камеры, тонкими деталями и ярким emissive проходят сравнение без устойчивого ghosting, мерцания и неправильных сбросов истории.

### Этап 8. Масштабирование и выпуск

1. Добавить frustum culling, сортировку по pipeline/material и instancing повторяющихся мешей. LOD и Forward+ вводить по профилю конкретных сцен.
2. Убрать повторные per-frame поиски ассетов и повторяющийся лог ошибок из горячих путей; обновлять render bindings при изменении ресурса или компонента.
3. Ввести бюджеты CPU/GPU памяти, eviction и безопасную повторную загрузку ресурсов. Проверить GPU lifetime при удалении больших групп объектов.
4. Добавить shader/pipeline cache с ключом версии, backend, параметров и исходников. Воспроизводимо поставлять необходимые shader variants вместе с Player.
5. Проверить D3D12 как основной Windows backend, Vulkan как дополнительный и отдельный набор возможностей OpenGL. Fallback не должен скрывать реальную причину отказа.
6. Прогнать длительную работу, многократный resize/Play/Stop, отсутствие ассетов, повреждённые материалы, потерю устройства и запуск на чистой машине.

Критерий завершения: целевая сцена укладывается в предварительно зафиксированные бюджеты времени и памяти; нет роста ресурсов при повторении сценариев; сборка игры запускается без SDK разработчика.

## Контрольные результаты

1. После этапов 0–2: надёжный многовидовой вывод, материалы и корректный цвет.
2. После этапов 3–5: законченная статическая сцена со светом, тенями и прозрачностью.
3. После этапа 6: пригодные для новеллы анимированные персонажи.
4. После этапов 7–8: стабильная картинка и проверенный путь выпуска.

Каждый этап должен завершаться небольшой демонстрационной сценой, содержательным автоматическим тестом и замером на целевом оборудовании. Наличие классов и подключённых библиотек не считается завершением этапа.

## Опорные материалы

Выбор реализации должен опираться на локальную закреплённую версию Diligent. Официальные примеры показывают offscreen rendering, несколько окон и glTF PBR: [Diligent samples](https://diligentgraphics.com/diligent-engine/samples/). Интеграция готовых эффектов описана в [Tutorial27 — Post Processing](https://diligentgraphics.github.io/docs/d7/de9/DiligentSamples_Tutorials_Tutorial27_PostProcessing_readme.html).

Контракт native QWidget и его атрибутов следует проверять по [документации Qt 6.8](https://doc.qt.io/qt-6.8/qwidget.html), соответствующей установленной ветке Qt. Эти источники служат справкой по интеграции; последовательность этапов выше — проектное решение для текущего состояния Sacura.
