## Одна модель данных и исполнения

Компонент — расширение существующего authored mechanic. Определения остаются
в `gameplay.mechanicDefinitions`, экземпляры в `gameplay.mechanics`, состояние
прохождения в `world.game.mechanicStates[instanceId]`. Объекты и сцены имеют
прежние идентичности. `componentInstances.js` управляет lifecycle и владельцами
handles внутри GameSession; тела методов исполняют существующие
`blueprintFunctions`, QuickJS, Events и operationRegistry. Второго ECS,
хранилища объектов, интерпретатора графов или жанрового runtime нет.

Формат определения расширяет mechanic schema v1:

| Поле | Контракт |
| --- | --- |
| `id`, `version`, `name` | Стабильный namespaced ID, положительная версия определения, редактируемое имя |
| `componentVersion: 1` | Явное включение компонентной семантики; старые определения сохраняют исполнение |
| `scopes` | Разрешённые владельцы: `object`, `scene`, `project` |
| `parameters` | Обычная object schema параметров экземпляра |
| `stateSchema`, `stateVersion` | Object schema сохраняемого состояния и его отдельная положительная версия |
| `initialState` | Авторские начальные значения поверх defaults state schema |
| `stateFromParameters` | Карта `поле состояния → имя параметра`; применяется при создании состояния новой игры один раз |
| `references` | Object schema именованных типизированных ссылок, в том числе `referenceType: mechanic` |
| `methods` | Карта стабильных локальных ID методов, см. ниже |
| `events` | Карта локальных ID событий: `name`, `payloadSchema`, `signalId` существующего сигнала |
| `lifecycle` | Необязательные `initialize`, `restore`, `enable`, `disable`, `destroy`: ID методов этого определения |
| `subscriptions` | Декларативные подписки: `id`, `signalId`, `methodId`, `match`, при необходимости `reference`, `passPayload` |
| `requirements` | Прежние версионированные требования к операциям; функции, Events, сигналы и ресурсы собираются транзитивно по типизированным связям |

`methods[methodId]` содержит `name`, object schema `parameters`, schema `result`
и `logic.functionId`. Графовая функция содержит исполняемые узлы. Для нового
кодового ресурса функция — производный индекс с `logicResourceId` и
`componentMethodId`, без фиктивного исполняемого графа и без отдельного текста.
QuickJS получает весь актуальный исходник и вызывает
`component.methods[methodId].run(ctx)` через прежний JS bridge. Сигнатуры и
результат проверяются общим диспетчером. Программные определения предыдущего
этапа с `mechanicScript` по-прежнему работают. `methodId` не зависит от
отображаемого имени, functionId или ID определения.

Ключи `methods` и `events` сохраняются при переносе; локальные ID функций,
сигналов и экземпляров переназначаются существующим импортёром. Имена методов
и их ID могут совпадать у разных определений без конфликта.

Для программного создания применяются прежние `createMechanicDefinition`
и `addMechanicInstance`. Рабочий пример:
[fixture LockedDoor](../engine-web-prototype/frontend/tests/fixtures/componentDoor.js).
В определении нет привязки к имени LockedDoor в исполнителе.

Экземпляр содержит `id`, `definitionId`, `definitionVersion`, `scope` владельца,
`values` параметров, `references`, `enabled`, имя подключения `name` и
необязательные постоянные `fieldBindings`. Изменение `values` в проекте
применяется при новом запуске; runtime-изменения состояния не переписывают
проектные defaults. Включение в прохождении сохраняется отдельно в lifecycle
record, исходный `enabled` проекта не изменяется.

## Ресурсы реализации и редактор

Проект сохраняет `logicResources[]`. У ресурса есть `id`, `version: 1`,
`kind`, `name`, `path` и `definitionId`; определение ссылается обратно через
`logicResourceId`. Путь вида `Компоненты/Counter.js` виден в библиотеке и
проводнике ресурсов и редактируется в свойствах. Это локальный ресурс внутри
сохраняемого проекта, а не внешний модуль или путь к исполняемому host-файлу.

| kind | Авторитетное содержание |
| --- | --- |
| `component.code` | Единственный `source`: JS с литеральной декларацией `component`, helpers и настоящими `run(ctx)` |
| `component.graph` | Методы в прежних `functions[].nodes`, schemas/сигналы/lifecycle в связанном определении |
| `behavior.tree` | Редактируемые `nodes/root` дерева и обычные графовые методы компонента поведения |

Для кода `parameters/state/references/methods/signals/lifecycle/subscriptions`
объявляются рядом с реализацией в одном исходнике. Сохранение статически
получает schemas и обновляет индекс определения. `locations` — производные
координаты методов; `dependencies` — прежняя переносимая таблица привязок;
`signalBindings` сохраняет project IDs собственных сигналов без внедрения их
в текст. Дублирующиеся ключи и прямые ID-ссылки в метаданных отвергаются.
Синтаксис QuickJS проверяется без исполнения тела программы.

`source` не имеет независимо редактируемой compiled-копии. Ресурс хранит
`status: draft/ready/error/review`, fingerprint сохранённого текста и
`approved`. Изменённый, ошибочный или импортированный исходник блокирует
запуск связанного компонента. Старый индекс сохраняется для диагностики
вызовов, но предыдущий текст тайно не исполняется. Черновик с ошибкой остаётся
в проекте после повторного открытия. Это явное требование текущего этапа;
прежние JS-механики со своим контрактом последней рабочей версии сохранены.

Путь автора: **Создать → Компонент → написать JavaScript →
сохранить → Добавить экземпляр**. Нужен только новый тип, не пресет/функция/Event.
Новый тип автоматически попадает в библиотеку проекта и **Добавить компонент**.
В инспекторе экземпляра редактируются настройки и именованные ссылки. Общий
исходник явно применяется ко всем его экземплярам. Методы, состояние, ссылки,
hooks и обработчики сигналов объявляются в этом исходнике.

`componentMethodChoices` строит палитру из актуальных определений, включая
только что опубликованные методы. Узлы показывают отдельные порты получателя,
каждого аргумента и результата, а также управляющие связи. Вычисления и
ветвления остаются узлами обычного Blueprint. Идентичность вызова хранит
определение/версию и стабильный ключ метода; другой тип с тем же ключом
не подставляется. Переименование display name безопасно; удаление ключа
оставляет диагностируемый разрыв. Двойной клик открывает реальную реализацию,
возврат сохраняет вызывающий граф и его положение. Кодовый метод вызывает
графовый через тот же `engine.invoke`, как граф вызывает кодовый через операцию.
Произвольный JS автоматически в граф не переводится; read-only Code у графа
остаётся представлением того же графа.

Синтаксическая ошибка показывает путь/строку/столбец, ошибка JS — путь/строку,
компонент и метод; ошибка графа добавляет function/node ID. Сохранённая
исправленная программа гарантированно применяется при следующем Play.
Hot reload выполняющейся VM не реализован.

## Вызовы и контекст

```js
await game.callComponent(instanceId, 'set-locked', {value: false}, context);
const task = game.startComponentTask(instanceId, 'interact', {}, context);
task.cancel();
await task.promise;
```

Для Events, истории, UI, ввода и графов зарегистрирована общая операция
`sacura.component.call@1` с параметрами `instance` (typed mechanic reference),
`methodId`, `args`. Зависимые схемы `componentArguments` и `componentResult`
берут типы из выбранного метода, включая `void`. Это тот же диспетчер,
что `game.callComponent`; вызов через старый `callMechanic` для компонента
отвергается с предложением выбрать метод.

JS-контекст метода:

- `args` — только аргументы этого вызова; `params` — настройки экземпляра.
- `state` — проверяемое сохраняемое состояние конкретного экземпляра.
- `self` — typed mechanic reference на этот экземпляр; `owner` — ссылка
  на его конкретный объект, сцену или проект.
- `refs` — назначенные именованные ссылки. Отсутствующая/удалённая связь
  даёт ошибку; игрок и первый похожий объект не подставляются.
- `context.source/target/initiator` — исходные адресаты события;
  `context.mechanicInstanceId/componentTaskId` — текущие экземпляр и задача.
- `engine`, `global` — прежние игровой API и переменные проекта.

`engine.invoke(selfOrReference, methodId, args)` вызывает конкретный экземпляр,
`engine.emit(localEventId, payload)` проверяет schema события и публикует его
через RuleRuntime с `source: {type: 'mechanic', id: instanceId}` и
`emitterInstanceId`. Графы читают `params/refs/self/owner/context` теми же
выражениями `get`, методы вызывают общей операцией. JS остаётся в QuickJS без
DOM/Node/сети; host callbacks из пакетов не регистрируются.

Для подписок `match: owner` — точное совпадение target объекта, sceneId сцены
или подписка проекта. `match: component` сравнивает `emitterInstanceId` с
назначенной mechanic reference; `match: any` — явная подписка без фильтра
владельца. По умолчанию метод получает `{}`; `passPayload: true` передаёт payload
сигнала как аргументы с обычной проверкой типов. Подписки выполняют отдельные
задачи экземпляра; публикация сигнала не означает join всех этих задач.
Повтор той же подписки в cause chain диагностируется как цикл.

## Состояние и lifecycle

1. Новая игра создаёт состояние каждого экземпляра: defaults схемы →
   `initialState` → `stateFromParameters` из его настроек. Копии не разделяют
   изменяемые структуры. Значения сохраняются и при уходе из сцены.
2. При активации владельца разрешаются и проверяются параметры/ссылки,
   один раз вызывается `initialize`, затем устанавливаются подписки и
   вызывается `enable`. Lifecycle hooks не принимают обязательных аргументов.
   Инициализация может вызвать другие методы того же экземпляра.
3. До событий `BEFORE` первой реплики компоненты сцены уже доступны. Следующая
   реплика той же сцены не создаёт их заново, не сбрасывает state, не вызывает
   initialize/enable и не добавляет подписок. Смена сцены снимает handles старых
   владельцев; project-компоненты продолжают существовать.
4. `setComponentEnabled(id, false)` немедленно отменяет задачи/ожидания и снимает
   подписки, Events, таймеры и дочернюю работу этого экземпляра; доступный
   владелец получает `disable`. Включение сохраняет state и вызывает `enable`.
5. `destroyComponent(id)` освобождает handles, вызывает `destroy` для доступного
   владельца и сохраняет tombstone. После загрузки уничтоженный компонент
   не включается снова. Удалённый/неактивный владелец не получает world effects;
   cleanup всё равно синхронно освобождает handles. Остановка сеанса синхронно
   освобождает ресурсы; author hooks при shutdown не запускаются.

`componentLifecycles[instanceId]` хранит только `stateVersion`, `initialized`,
`enabled`, `destroyed`. Map handles, AbortController, VM, callback и Promise
не сериализуются. Save доступен по прежнему правилу завершения текущей работы.

Перед загрузкой проверяются состояние и его версия **до остановки текущей игры**.
Отсутствующая или неизвестная `stateVersion` приводит к понятному отказу с
требованием миграции. Автоматического fallback на defaults нет. Программный
API миграций ещё не реализован. Существующий compatibility fingerprint
по-прежнему защищает от загрузки save в изменённую программу проекта.

Загрузка сохраняет восстановленные значения выше defaults, не повторяет
`initialize`, стартовый сигнал игры, starter inventory или события входа
истории. Восстанавливаются подписки, вызываются `restore` и `enable`;
отложенный/выключенный экземпляр получает `restore` при следующей активации.
Поэтому стартовые игровые эффекты следует помещать в `initialize`, а
восстановление временных ресурсов — в `restore/enable`. Если экземпляр ещё
ни разу не активировался до save, его initialize остаётся первым, а не повторным.

## Задача и владение ресурсами

Каждый вызов получает ID, Promise и AbortController отдельно от компонента.
Handle имеет `status`: `running` (включая ожидание), `completed`, `cancelled`
или `failed`. Завершение метода не уничтожает экземпляр. Рекурсия ограничена
16 уровнями, одновременно допускается до 128 задач компонентов, сохраняются
прежние лимиты графов/QuickJS.

Вложенный вызов метода связан с отменой родителя. `wait/waitSignal`, async
операции, native Events и `engine.start` используют прежний механизм работ
с дополнительным владельцем задачи/экземпляра. Отмена задачи не отключает
компонент и не отменяет соседний вызов, даже на том же экземпляре. `join/cancel`
не принимают handle чужой компонентной задачи. Отключение экземпляра отменяет
всю принадлежащую ему работу; следующий запуск игры очищает старые подписки.

Декларативные подписки принадлежат компоненту, `waitSignal` — вызову.
Native timer start из компонента создаёт **таймер компонента**, который может
жить после завершения метода. Ключ включает владельца, instance ID и имя;
два компонента на одном объекте не перезаписывают таймеры друг друга.
Отключение/уничтожение снимает только таймеры своего экземпляра.

После отмены VM и граф проверяют активность до следующих записей/операций;
поздний resolve ожидания не продолжает изменять мир. Уже завершённые эффекты
не откатываются. Доверенный native async executor обязан проверять
`context.assertActive()` после await и до записи во внешний мир — runtime
не может отменить побочный эффект произвольного установленного host-кода.

## Native-состояние

HP и боезапас сохраняют существующие authoritative `actors/weapons` records;
компонент использует `sacura.health.*` / `sacura.weapon.*`. Зеркальные изменяемые
`state.hp`/`state.ammo` не вводились. Для двери `IsLocked` принадлежит экземпляру,
а открытость — прежнему `world.doors`. Новые `sacura.door.read/write` являются
адаптерами к той же записи, которую используют native door Event и renderer.
В fixture нет второго `IsOpen`. Физика, коллизии, движение и рендер не переведены
в async Events на кадр; их существующие ограничения этот этап не расширяет.

## Behavior Tree как ресурс компонента (прежняя реализация)

В прежнем UI `Создать → Компонент → Behavior Tree` создавало ресурс и обычное определение
компонента с `behaviorTree: {treeResourceId, interval: 0.1, autoStart: false}`.
Подключение подготавливает компонент без запуска дерева. Публичные графовые
методы `start` / `stop` вызывают общие операции run/stop. Запуск — отдельная
ожидающая задача; для боя назначьте ей lifetime явно, см. раздел интерфейса.
Старые сохранённые определения без `autoStart: false` сохраняют прежний режим. Дерево редактируется
в ReactFlow: selector/sequence с порядком детей, condition, задачи методов,
чтение данных, константы, сравнение, сложение и умножение. Управляющие связи
дерева и информационные провода видны отдельно. Задачи выбираются из той же
динамической библиотеки методов и открываются двойным кликом с возвратом.
Вкладка «Методы поведения» позволяет автору менять правила и состояние
поведения обычным графом, а не только выбирать встроенный алгоритм.

`GameSession.tick` вызывает bounded обход с заданным интервалом. Нет запуска
Rule на каждый кадр или клонирования проекта при обновлении дерева. Conditions
читают `state/params/refs/global`, вычислительные выходы оценивает прежний
`evaluateExpression`. Tasks запускаются только общим `startComponentTask`.
void/true означают Success, false — Failure, также разрешены строковые
Success/Failure/Running. Незавершённый Promise — Running; возвращённый Running
повторно вызывает задачу при следующем обновлении. Завершившийся корень
начинает новый обход при следующем обновлении. Предки активной ветви
проверяются повторно; изменение guard отменяет ожидающую старую задачу.

`componentHandles[instanceId].tree` содержит временный controller, Promise,
результаты текущего обхода и epoch. `world.game.componentBehaviors[instanceId]`
содержит наблюдаемый status/nodeId/ticks/error. Результаты методов и их
сохраняемое состояние остаются в `mechanicStates`. При смене ветви, отключении,
уничтожении или остановке владельца его работа отменяется; epoch и обычные
проверки задач не допускают поздних эффектов. Чужая ветвь/экземпляр продолжают
работать. Ошибка задачи сообщает путь и node ID и останавливает дерево
до перезапуска владельца без повторяющихся ошибок каждое обновление.

Continuation JS/Promise не сериализуется: прежнее правило save требует
завершения текущей работы, после загрузки обход дерева начинается с корня
на восстановленном state. Source/dependencies и содержание дерева входят в
compatibility fingerprint save; перенос виртуального пути и координат графа
не меняет программу. Редактор дерева пока не содержит decorators,
parallel-композитов, breakpoint/debugger и отдельного UI частоты tick.
Старый native pursuit остаётся прежней системой и не называется Behavior Tree.
Raycast, физика и рендер остаются системными примитивами.

## Перенос и редактирование

Используется общий authoring package с capability `mechanic.components@1`: данные
v1/v2 читаются по совместимости; исходники и корень component используют
[явный v3](AUTHORING-PACKAGE-V3.md). Старый data-валидатор не расширяет доверие к JS. Сбор functionId/signalId и typed references
охватывает все методы, lifecycle, события, подписки и зависимости JS.
Методы не теряют stable keys при remap. Предпросмотр и атомарное применение,
привязки объектов и конфликтующие ID остаются в существующем импортёре.
Неизвестная версия компонента/отсутствующая реализация отклоняется заранее.

Ресурсы входят в общее транзитивное замыкание (исходники — только v3) с capability
`component.resources@1`, для дерева — `behavior.tree@1`; JS также требует
`mechanic.javascript@1`. Экспорт включает один исходник с таблицей зависимостей,
графовые методы, узлы дерева, собственные сигналы и назначенные ссылки.
Импорт проверяет структуру/версию/декларацию, переназначает IDs, устраняет
конфликт пути и применяется атомарно. **JS при импорте не исполняется**,
`approved` сбрасывается и ставится `review`; принимающий автор открывает
и сохраняет локальный исходник для запуска. Неподдержанный capability
отвергается до применения. Экспорт не требует прикреплённого экземпляра:
кнопка ресурса экспортирует определение без фиктивного экземпляра. Начальные
подключения и другие определения выбираются явно.

Копия с общим определением разделяет реализацию и имеет отдельный state;
независимая копия клонирует исходный ресурс, функции, дерево и собственные
сигналы с новыми IDs/путём. Заготовка не содержит живого state/Promise.
Тесты A → B → C изменяют исходник B и запускают вариант C без проекта A;
тест дерева дополнительно проверяет перенос task sources и references.

## Этап интерфейса подключений и связи со сценой

Основной путь: **Иерархия → объект → Компоненты → именованное подключение**.
Инспектор показывает параметры по schema, типизированные ссылки, enabled,
владельца и во время Play — разрешённое runtime-состояние только для чтения.
Имя подключения отдельно от имени типа: «Складской замок» и «Архивный замок»
используют один LockedDoor. Выбор конкретного подключения никогда не означает
«первый компонент этого типа». Кнопка общей реализации открывает код/граф
в центре; баннер сообщает число затрагиваемых подключений.

**Создать независимый вариант** — явная отдельная копия определения, ресурса
и зависимостей через прежний механизм копирования. Обычное подключение
переиспользует исходник. В «Игровых механиках» определения ресурсов отделены
от прежних подключений и от методов открытой реализации. Новые штатные
Health/Weapon используют одно общее определение и общий набор функций типа.
Существующие локальные авторские варианты не объединяются автоматически.
Их параметры, owner и native runtime-state доступны отдельно в инспекторе;
штатные handlers пока имеют прежний формат, а не публичные компонентные методы.

### Один выбор вызова для всех редакторов

`ComponentCallFields` используется в фазах истории **До текста / Вместе с
текстом / После ответа игрока**, Event/Sequence, действиях ввода, действиях
кнопок виджетов и настройке взаимодействия объекта. Выбор: owner object/scene/
project → конкретное именованное подключение → метод → аргументы по schema.
Поиск и подписи используют имена; сохраняются typed references на ID.
Заголовок действия: «Дверь склада → Открыть», JSON туда не сериализуется.
Фаза истории добавляет обычный Event с общей операцией, второго runtime нет.

У объекта `interactionCall` — та же операция `sacura.component.call`.
Клик по адресованному mesh и point-input направляются к ней до обычного
продолжения диалога, независимо от активности жанровых native-механик.
Отрицательный результат в gate оставляет ожидание взаимодействия. Объект
с другого/удалённого owner не заменяется похожей дверью: диспетчер сообщает
имя подключения/владельца и недоступность. Для будущей сцены можно заранее
изменить сюжетную переменную и назначить её постоянным источником поля.

### Литерал, снимок и постоянный источник

| Настройка | Семантика |
| --- | --- |
| Аргумент «Задать непосредственно» → Нет | Непосредственный bool `false`, вызывает выбранный метод |
| Аргумент «Переменная истории · один раз при вызове» | Выражение `op: variable` с typed variable reference; вычисляется один раз до выполнения метода |
| Инспектор → Постоянные привязки к истории | `fieldBindings: [{target: state/parameters, field, variable: typed reference}]`; каждое чтение получает актуальное значение источника |

Постоянная привязка поддерживает верхнеуровневое поле объявленной schema,
включая коллекцию/объект целиком. Редактор предлагает переменные совместимого
текущего типа. Вложенные пути не вводятся вручную. Связанное state-поле
удаляется из raw `mechanicStates`: изменяемой копии нет. Чтение в JS, графе,
условии Rule, Behavior Tree и debug-инспекторе использует view источника.
После await bound params также перечитываются; args остаются снимком.
Запись в связанное поле, включая изменение элемента коллекции, запрещена
с объяснением «измените переменную истории явно». Двусторонней синхронизации
нет. Defaults параметров остаются настройками инициализации, не вторым
runtime-состоянием. Save хранит переменную и связь, но не зеркальное state-поле.
Переименование переменной/объекта сохраняет ссылку по ID.

### Задача запуска и длительность поведения

Выбор **Дождаться завершения метода** использует `sacura.component.call`.
Выбор **Запустить задачу и продолжить** использует `sacura.component.start`,
возвращает прежний work handle и требует явных `lifetime` и `lifetimeOwner`:
сцена, проект или конкретный включённый компонент. Отмена вызвавшего Event/
Sequence не останавливает такую работу. Остановка lifetime-владельца или
целевого компонента отменяет её и дочерние ожидания. Соседние задачи и
постоянные компоненты сцены сохраняются. Ошибка фоновой работы диагностируется.

Для боя Sequence явно вызывает `start` компонента поведения с выбранным
владельцем длительной задачи. Подключение Health/нового Behavior Tree само
бой не запускает. Явно запущенное дерево продолжает native ticks при следующей
реплике и даже при `mechanics: gameplay-node`; Pause/Stop игры его останавливают.
Оно по-прежнему не копирует проект через очередь Rules на каждом кадре.
Сохранение ожидающих задач/боевой continuation этим этапом не добавлено.

### LockedDoor и фактическая приёмка

Кнопка **Добавить дверь с замком** устанавливает обычный редактируемый кодовый
ресурс из `componentExamples.js` и адресует взаимодействие на его `interact`.
Повторное добавление переиспользует тот же ресурс. В executor нет проверки
имени LockedDoor. Начальный `IsLocked=true` берётся из параметра экземпляра
один раз. `setLocked(false)` меняет только его state и не открывает дверь.
`interact` сообщает «Заперто» или вызывает `open`. `open` ожидает конечную
native-анимацию `sacura.door.animate`, затем отправляет собственный сигнал.
Открытость остаётся в `world.doors`, временный прогресс — `world.doorMotions`;
отмена фиксирует достигнутый угол и не допускает позднего открытия.
Сообщение видно и в новелле без HUD.

  архив связан с ней постоянно, склад во второй реплике получает разовый снимок;

## Этап переносимости, готовой игры и save

Подробные реализованные форматы: [пакет v3](AUTHORING-PACKAGE-V3.md),
[экспорт и сохранения](GAME-EXPORT-SAVES.md). В текущем checkout обнаружен
неявный перенос `source` через v2 при прежнем запрете `script/code`.
Теперь `packageSourceContract.js` различает data v1/v2 и явный v3 SDK:
исходник не устанавливает расширение и не регистрирует host API. Старые data
пакеты продолжают читаться; промежуточный JS-v2 нужно переэкспортировать из проекта.

Экспорт ресурса в центре имеет список определений и необязательный выбор
начальных подключений. Корень `component` содержит definition entries и
отдельные instance entries; общий source включается один раз. Обязательные
зависимые подключения собираются транзитивно. Preview перечисляет состав,
показывает именованные inputs, требования и конфликты. Импорт также показывает
readonly исходники без выполнения. Apply атомарен, source получает review.
Авторство, лицензии и версии A/B остаются в sources при повторном экспорте.
Сохранение локального исходника сохраняет уникальность имени в библиотеке.

Сборка HTML отбирает используемые component definitions/resources/functions
из копии проекта, встраивает ресурсы и проверяет status, индексы и синтаксис
до выдачи файла. Неиспользуемый сломанный source остаётся в редакторе, но не
ломает HTML. Legacy публичные функции и обычные Events сохраняются
консервативно; полного tree shaking всех авторских каталогов нет.
Manifest player не содержит компонентов редактора. В HTML используются
прежние GameSession/QuickJS, диспетчер методов, состояние и отмена.

Save v3 добавляет явную таблицу instance → definition/version/stateVersion/
scope/references/fieldBindings. Runtime-state остаётся в mechanicStates,
сюжетные переменные и native HP/боезапас/двери — в прежних записях. Save v1/v2
читаются с прежними проверками. Загрузка валидируется до замены мира и не
повторяет initialize, награду, starter inventory и подписки. Unlocked дверь
остаётся unlocked. Начальные настройки не становятся текущим runtime-state.

Поддержанный checkpoint требует завершения или явной остановки async методов.
Незавершённый Promise сообщает компонент/метод до записи в storage, прежний
save сохраняется. Native timer уже сериализуем: remaining/owner продолжаются
после load. Произвольные VM/JS continuations не сохраняются; enabled новое
дерево без контрольной точки в save отвергается. Автоматический повтор Start
или второй AI при загрузке не добавлен.

Следующие этапы и ограничения:

- **Миграции save:** явные версионированные преобразования с предпросмотром.
  Сейчас безопасный отказ, не автоматическая миграция.
- **Native-редактирование:** постепенный перенос штатных составных handlers
  в публичные методы. Поголовная конверсия native behaviors не выполнена;
  исходники новых авторских компонентов и правила новых деревьев открываемы.
- **Ручная приёмка переноса двери:** полный путь привязок и повторного экспорта
  через редактор после UI этапа. Headless A → B → C Counter/LockedDoor не
  объявляет выполненной полную [приёмку двери с ключом](ACCEPTANCE-DOOR-WITH-KEY.md).
- **Расширение редактора:** debugger, breakpoint, дифф/история
  исходников и расширенные BT-узлы не добавлены. Частота дерева пока в данных.
  Graph result type задаётся в UI, сложные вложенные result schemas не имеют
  отдельного специализированного редактора. Применение исходника — следующий Play.
- **Код:** нет npm/ES modules, DOM/сети, hot reload или двусторонней трансляции
  произвольного JS и графа. Не следует размещать project IDs в исполняемом
  тексте: для переноса нужны refs или dependency table. Верхнеуровневый JS
  исполняется на вызов, сохраняемые данные должны быть в state.
- **Behavior Tree save:** сохранение ожидающей continuation не поддерживается;
  после разрешённого idle-save дерево возобновляет обход с корня на state.
- Локальные предыдущие изменения checkout сохранены; магазин, аккаунты,
  платежи, облачная синхронизация не добавлены.

Проверка трёх принципов текущего этапа:

- **Простота:** новый тип создаётся в UI без пресета, JSON и регистрации в enum;
  его два экземпляра добавляются/настраиваются через инспектор. Готовые механики
  сохраняют прежний путь. Раскрытие реализации и возврат проверены в UI.
  Для нового кодового поведения требуется JavaScript по явному заданию автора;
  готовый Counter повторно используется только настройкой step.
- **Редактируемость и переносимость:** тот же source реально исполняется,
  ошибочный текст сохраняется, графовые порты/дерево редактируются; автоматические
  A → B → C и независимая копия проверяют исполнение изменённого варианта,
  remap и отказ запуска импортированного кода до просмотра/сохранения.
  Проверены конфликт пути без расширения, независимая копия дерева и отказ
  загрузки старого save после изменения source до замены текущего мира.
  Полная ручная приёмка двери не заявляется.
- **Универсальность:** Counter и Behavior Tree работают без героя/оружия через
  общие определения/экземпляры, Events, schemas и операции. Native tick не
  копирует проект через сюжетные Rules. Отдельного ECS или жанрового runtime нет.


Три принципа для интерфейса сцены/истории:

- **Простота:** живой браузерный сценарий пройден от иерархии без ID/JSON;
  параметры и общий исходник явно различаются, вызов имеет единый picker.
- **Переносимость и редактируемость:** source LockedDoor открываемый и общий;
  копия создаётся явно, поле-источник и получатель переносятся типизированными
  ссылками. Автоматически проверен импорт связанной двери и независимый runtime;
  ручной полный A → B → C не объявлен закрытым.
- **Универсальность:** те же операции обслуживают объект, scope сцены/проекта,
  историю, ввод, UI и фоновые задачи. Бой запускается явно; HP/боезапас остаются
  в native adapters без второго изменяемого источника. Старые native handlers
  постепенно переводятся в публичные методы, автоматической полной конверсии нет.

## Этап: действующие шаблоны на компонентах

### Уточнения контрактов после интеграции

- Доставка сигнала запускает отдельную задачу получателя. После доставки она
  не наследует `nativeRunId` опубликовавшего Event: остановка издателя не
  отменяет уже принятую чужую работу. До доставки отменённый издатель не может
  публиковать поздние эффекты. Подписка и задача по-прежнему принадлежат получателю.
- Ошибка сохраняет цепочку вызовов и конкретный внутренний receiver даже при
  проходе через QuickJS и вложенный вызов. SDK-bridge восстанавливает исходный
  host Error по временному токену текущей VM; ошибки автора не могут назначить
  произвольную идентичность host-ошибки. Добавленный в `catch` текст сохраняется.
- `componentDiagnostic` содержит владельца, подключение, определение/версию,
  метод, ресурс/функцию и доступные строку/колонку/узел. Панель ошибки остаётся
  в сцене и останавливает Play перед переходом в реализацию. Новый запуск
  очищает диагностику; она не является сохраняемым состоянием компонента.
- Дублирование/вставка объектов копирует начальную конфигурацию подключений,
  переиспользует определения и переназначает внутренние ссылки всей копируемой
  группы. `interactionCall` адресует копию. Native adapters оружия, здоровья,
  предметов и инвентаря также переназначаются. Текущее состояние Play не копируется.
  Буфер объектов хранит снимок конфигурации на момент копирования. Между разными
  проектами компоненты переносятся пакетом с предпросмотром, не буфером геометрии.
- Сообщения SDK видны также в standalone игре без HUD и во время диалога.
  Компонент обратной связи сам импортирует свой CSS: стили больше не зависят от
  editor bundle. `npm test` предварительно собирает player, исключая проверку
  устаревшего или отсутствующего сгенерированного runtime.

## «Последний обход» и кликер — 20 октября 2026

Каталог содержит шесть проектов. В основных карточках появился point & click
хоррор «Последний обход»; UI-кликер находится в раскрываемом разделе «Ещё».
Хоррор — обычный пакет v3, без веток runtime по имени шаблона.
Генератор `templates/horror.mjs` вызывается из `templates/projects.mjs`;
`build:templates` обновляет его публичный пакет вместе с остальными.

Сцена содержит один `HauntedRoom`, общий `HauntedProp` для предметов и общий
`LockedDoor` для выхода. Правила выхода, этапы загадки, отражение, сигналы,
тексты и дальность взаимодействия открываются в исходниках/инспекторе.
Игрок выбирается через команду «Игрок» в иерархии; камера — thirdPerson,
WASD — движение, ЛКМ — осмотр. `GameControls.js` поддерживает ПКМ + мышь
без захвата курсора через существующую операцию camera.look. Контекст ввода
принадлежит компоненту сцены и сохраняется при переназначении ID пакета.

Подготовка нового обхода скрывает силуэт/аварийный свет и задаёт начальный
ракурс один раз через initialize. Загрузка использует сохранённый мир и
объявленное состояние, без повторной подготовки. Получение предохранителя,
питание, запись и выход исполняются методами с явными ссылками. Выход снимает
замок отдельно и ожидает Open, после чего входит в финал истории.

Кликер использует один Counter, один Reward и один PeriodicReward. Новый
метод collect обращается к тому же Reward с текущим rate, что и tick:
улучшение влияет на нажатие и таймер. Остановка/запуск не создают второй
таймер. Игровой экран собран из редактируемого HUD, без оформления,
зашитого в React. Существующие пользовательские проекты не переписываются;
обновлённый пример создаётся из карточки в «Ещё».

Дополнительные файлы: `HauntedRoom.js`, `HauntedProp.js`, `PeriodicReward.js`,
`horror-clicker.test.js`, проверки ввода, walkthrough, переносимых шаблонов,
`ProjectHome.jsx`, `ProjectArtwork.jsx`, стили каталога и переводы.
Результаты браузерной приёмки и границы перечислены в COMPONENT-ACCEPTANCE.md.

Production-хостинг JS SDK требует `script-src 'self' 'wasm-unsafe-eval'`: QuickJS
инстанцируется в WebAssembly. Нельзя заменять это широким unsafe-eval для
host JS. Контракт браузера: [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src#unsafe_webassembly_execution).
Проверка HTTP перед приёмкой: `node deploy/check-runtime-policy.mjs URL`
из engine-web-prototype; импорт и просмотр исходников gameplay не запускают.

Серверное хранение также поддерживает явный storyless-контракт v2: пустые
chapters, enabled gameplay, storyPolicy.mode=none и доступная scene.location
в непустом списке сцен с уникальными ID. Отсутствие главы само по себе не
ошибка кликера; прочие проекты сохраняют прежние проверки. Исправление
находится в server/storage.js, реальная API-регрессия — server/tests/storage.test.js.
